# Evaluation report

This report documents the actual, reproducible results of running the
SpecVision AI pipeline against the labeled evaluation set. Nothing here is
simulated or hand-picked after the fact -- the numbers below are read
directly from `evaluation/results/evaluation_offline.json` and
`evaluation/results/evaluation_live.json`, generated by
`evaluation/runner/run_evaluation.py` on 2026-10-12.

## How to reproduce these numbers

```powershell
cd backend
.venv\Scripts\python ..\evaluation\runner\run_evaluation.py --mode offline   # no network, no API key
.venv\Scripts\python ..\evaluation\runner\run_evaluation.py --mode live      # real Groq calls, needs GROQ_API_KEY
```

Each run overwrites `evaluation/results/evaluation_<mode>.json` (machine-readable)
and `evaluation/results/evaluation_<mode>_summary.md` (human-readable).

## Dataset

16 labeled cases (`evaluation/data/cases.json`), 7 of them paired with real
photographs (`evaluation/images/`, sourced from Wikimedia Commons under CC
BY / CC BY-SA licenses -- see `evaluation/images/PROVENANCE.md`). The set
deliberately includes: complete and vague briefs, an implausible carat
value, a metal/purity contradiction, two simulated LLM-provider-failure
cases (malformed JSON repair, total failure -> safe degradation), a brief
engineered to hit a known catalog item, a brief engineered to match
nothing in the catalog, and seven real photos spanning different metals,
stones (diamond, citrine, no stone at all), compositions, backgrounds,
and resolutions.

**Limitations of this dataset, stated plainly:** 16 cases and 7 images is
enough to exercise every code path and catch real bugs (and it did -- see
below) but it is far too small to produce statistically meaningful
accuracy estimates. A single case flipping right/wrong moves a field's
accuracy by 10-100 percentage points. Nothing in this report should be
read as a claim about production-grade performance.

## Methodology note: what counts as "gold"

Gold-standard categorical/numeric fields were authored against the
**brief text only** -- not against what a human can see in the paired
photo, and not against domain inferences that go beyond the literal
words (e.g. "platinum" does not get scored as implying a specific
purity in the gold standard, even though it almost always does in real
jewelry). This is a deliberate, conservative choice: extraction operates
on text, so extraction accuracy should be judged against text, and the
"approximate" visible-stone counts used for CV grading are kept in a
separate field (`reference_visible_stone_count`) precisely so the two
evaluation axes (text understanding vs. image understanding) aren't
conflated. This choice is visible in the results below -- it is why the
offline rule-based extractor, which encodes the "platinum = 950 purity"
convention explicitly, outperforms the live LLM on `metal_purity`
despite being the simpler system.

Several labeling mistakes were found and corrected *during* this
evaluation (not before it): three cases originally had `metal_color` or
`setting_type` gold values set from the photo rather than the brief
text, and one case's offline extractor rule invented a specific
`band_width_mm` value for the qualitative phrase "slim band" with no
number in the text. Both were genuine bugs (a labeling bug in the
dataset, and a fabrication bug in the extractor) and both are fixed in
the current code/dataset -- see "Fixed during evaluation" below.

**Unknown-handling** (did the system correctly say "unknown" instead of
guessing, on cases where the gold standard is null): offline abstained
correctly on every field it wasn't sure of (0 fabrications across all
fields). Live mode fabricated a value on 4/9 `metal_color`-unknown cases
and 1/5 `center_stone_shape`-unknown cases -- in every one of those
cases the model inferred a plausible-but-unstated attribute (e.g.
`metal_color=white` for a "silver" or "platinum" item that never used
the word "white"). See the methodology note above and failure #3 below.

**Aggregation method:** categorical accuracy = exact string match against
gold, computed only over cases with a non-null gold value for that
field. Numeric accuracy = within tolerance (listed per field) of gold.
Cases where gold is null are scored separately as the unknown-abstention
rate, not mixed into the accuracy denominator -- a system that always
said "unknown" would score 0% accuracy (correctly, since it would be
useless) but 100% abstention (also correctly, since it never lied).

## The three worst failures

### 1. Classical CV confidently miscounts ornate filigree as gemstones (`case-15`)

**Case:** a real photo of a sterling silver ring with a large citrine and
an open filigree (pierced metalwork) band, **no side stones at all**.
The brief states this explicitly: "...an open filigree band, no side
stones."

**Expected:** `estimated_visible_count = 0`.

**Actual:** the classical CV pipeline reports **16** visible components,
with **HIGH confidence** and **no image-quality warnings** -- the
pipeline's own self-assessment gives no indication anything is wrong.
The filigree's pierced cutout pattern produces exactly the kind of
small, roughly-circular contours the Hough-circle/contour hybrid is
designed to find.

**Why it's still caught:** because the brief explicitly states "no side
stones," `cross_check_cv_vs_brief` computes a disagreement ratio of 16.0
(far above the 0.4 threshold) and raises `CV_BRIEF_COUNT_DISAGREEMENT`,
so the case correctly ends up `needs_review`. This is the system working
as designed -- but only because this particular brief happened to state
the side-stone count explicitly.

**Root cause:** the CV confidence policy has no signal for "these
detections look like they're tracing a continuous decorative pattern
rather than discrete objects" -- it only looks at count and raw image
quality (brightness/contrast/blur), both of which are fine on this
image.

**Is this honestly flagged?** Only conditionally. If the same photo were
paired with a brief that simply didn't mention side-stone count (a very
realistic scenario -- most of our own text-brief-only cases don't), the
CV result would propagate as a confident, unreviewed "16 visible
components," which is actively wrong.

**Proposed improvement:** add a geometric-regularity check -- decorative
filigree patterns tend to be densely packed with low variance in
inter-detection spacing along a continuous band outline, whereas genuine
set stones have more irregular spacing tied to a prong/channel layout.
A second-opinion rule ("detections cover >X% of the band's surface area"
or "detection count is improbably uniform") could downgrade confidence
even without a contradicting brief.

### 2. Severe overcounting on princess-cut stones against a textured background (`case-11`)

**Case:** a real photo of channel-set princess-cut diamonds along both
shoulders of a ring, photographed on a textured olive-colored surface.
Visually, there are roughly 10 side stones.

**Actual:** the pipeline reports **37** visible components -- more than
3x the true count.

**Is this honestly flagged?** Yes, and this is the system behaving well:
confidence is **LOW**, `IMAGE_QUALITY_INSUFFICIENT` fires, and
`suitable_for_automatic_use` is `False`. The >24-detection branch in the
confidence policy (`cv_pipeline.py`) exists specifically for this
pattern.

**Root cause:** princess-cut facets are angular and highly reflective;
each facet edge can independently satisfy the contour detector's
circularity threshold, and the textured background adds further
spurious contours. Non-circular angular cuts were a deliberate design
target (the brief warns not to assume every stone is round), but the
current circularity threshold (0.55) is still loose enough to accept
facet fragments as separate "stones."

**Residual risk:** the *raw number* (37) is still returned in the API
response alongside the low-confidence flag. A UI or downstream consumer
that displays the count without surfacing the confidence/warning
prominently would mislead a user. SpecVision AI's own frontend does
show them together (see `CVPanel.tsx`), but this is a real design
constraint worth stating explicitly: **the raw count field is not safe
to read in isolation** from `confidence` and `suitable_for_automatic_use`.

**Proposed improvement:** cap the returned `estimated_visible_count` at
a "capped_count (uncertain)" representation when confidence is LOW,
or require callers to explicitly opt into the raw number. We chose not
to do this in the current version because the brief asks for the actual
estimate to be returned (not hidden), but a product UI built on this API
should treat a LOW-confidence count as "no reliable number," not "a
possibly-wrong number."

### 3. The live LLM is not strictly more accurate than the offline rule-based extractor

**Case:** `metal_purity` accuracy is **1.00 offline vs. 0.80 live**
(same 10 cases, both runs). Concretely, for the brief "Platinum ring
with a sapphire centerpiece," the offline extractor correctly returns
`950_platinum` (it encodes the domain convention that platinum jewelry
is virtually always 950 purity), while the live model (`openai/gpt-oss-120b`
via Groq) returned `null` for the same brief in this run.

**Why this matters:** it's tempting to assume the LLM-based path is
strictly "smarter" than the deterministic fallback and that offline mode
exists only for when credentials are unavailable. The data doesn't
support that. The rule-based extractor's domain knowledge is narrow but
precisely encoded; the LLM's domain knowledge is broad but inconsistently
applied from one request to the next (the live run also fabricated
`metal_color=white` on 4 cases where the brief said "platinum" or
"silver" but never the word "white" -- a reasonable inference a human
might also make, but one that our (deliberately strict, text-literal)
gold standard scores as a fabrication).

**Is this flagged for review?** No, and arguably it should be: nothing
in the current pipeline cross-checks live-model output against the kind
of hand-codeable domain conventions the offline extractor already knows
(platinum/silver implying a white-toned metal, etc.). Confidence for an
LLM-inferred field is `MEDIUM` via `SourceType.MODEL_INFERRED`, which is
honest, but there's no flag specifically for "the model inferred
something our own rules would have derived more conservatively/directly."

**Proposed improvement:** run the offline rule-based extractor as a
*second opinion* even in live mode (cheap, deterministic, already
built), and raise a review flag when the two disagree on a field. This
would have caught both the `metal_purity` miss and the `metal_color`
over-inferences automatically, without needing a human to notice the
pattern across many requests.

## Fixed during this evaluation (for transparency)

Running the harness against real data surfaced genuine bugs, which were
fixed in the code (not worked around in the dataset):

1. **Crash on implausible user-stated values.** `RawExtraction`'s
   Pydantic bounds (originally `le=30` for carat) were tight enough that
   a literal user statement like "a 50 carat diamond" crashed the
   offline extractor with an unhandled `ValidationError` instead of
   flowing through to the plausibility-check/review-flag system that
   exists specifically to handle this. Fixed by widening the raw-schema
   bounds (a syntactic sanity net against hallucinated garbage) and
   leaving the domain-plausibility judgment entirely to
   `app/services/confidence.py`'s dedicated, tighter checks.
2. **False-positive substring matching.** The keyword extractor matched
   "pear" (a gemstone *shape*) inside "pearl" (a gemstone *type*) via
   plain substring containment, misclassifying a pearl ring's shape as
   pear-cut. Fixed with word-boundary regex matching.
3. **Word-number side-stone counts not recognized.** "eight moissanite
   side stones" failed to extract (only digit forms like "8 side
   stones" worked, and only with zero words in between). Fixed to accept
   number words and up to two intervening descriptor words, plus
   explicit "no side stones" phrasing -> 0.
4. **Fabricated band-width default.** The offline extractor mapped the
   qualitative phrase "slim band" to an invented `1.5mm`, violating the
   project's own never-fabricate principle (ironically, in the
   deterministic fallback that exists specifically to be more honest
   than an LLM). Removed; only an explicit numeric measurement is now
   extracted.
5. **Dataset labeling errors.** Several gold-standard values in
   `cases.json` were initially set from visual inspection of the paired
   photo rather than from the brief text actually being scored, which
   would have understated extraction accuracy for reasons that had
   nothing to do with the extractor. Corrected to reflect the stated
   methodology (score text extraction against text).

None of these fixes were "tuning to the test set" in the sense the brief
warns against -- each is a general code change (not a dataset-specific
hack) that was re-verified against the full pytest suite (51/51 passing)
after the change.

## Next steps if this were a longer-running project

- Grow the dataset past 100+ cases, with multiple human labelers and an
  inter-rater agreement check on the visible-stone counts (currently a
  single author's estimate).
- Add the offline-extractor-as-second-opinion cross-check described in
  failure #3.
- Add a geometric-regularity signal to the CV confidence policy (failure #1).
- Track live-mode accuracy over many runs (not one) to separate genuine
  model behavior from single-run noise -- Groq's free-tier models are
  not guaranteed to be deterministic even at `temperature=0`, and this
  report's live numbers reflect one run at one point in time.
